# 下一次实验任务：验证 1P-nD MLFQ 基线

## 目标与范围

先验证当前代码能真实完成：P 端 FCFS Prefill → P 内存保存 KV → D 主动领取 →
Decode 时间片耗尽 → KV 回传 P → 降级排队 → 任意兼容 D 恢复，以及超时晋级。
正确性通过后再测开销与公平性，不预设算法一定有提升，也不假定 P 的完成速率是 D 的 6 倍。

本文件只记录任务；本次不启动 GPU 实验。后续收到“跑实验”后按以下顺序执行，
遇到正确性问题先修复并复测，再进入性能阶段。代码保持简洁，优先复用已有接口。

## 当前状态

- 实现：`python/sglang/srt/disaggregation/mlfq.py`；启动参数和命令见本目录 `README.md`。
- 三个类：`Job` 保存状态，`MLFQPool` 管理全局三级队列，`MLFQRuntime` 连接推理与通信。
- P 单请求 FCFS Prefill，D 按 Q0/Q1/Q2 优先级、同级 FIFO 领取容量可满足的请求。
- 仅 Decode 执行时间消耗时间片；完整 KV 回传收到确认后，D 才释放显存。
- Q0→Q1→Q2，Q2 耗尽回到 Q2；等待超过阈值的 Q1/Q2 请求进入 Q0 尾部。
- 只有 `pull`、`update` 两类消息；递增领取凭证阻止旧消息修改新一轮执行状态。
- P 在 Prefill 前预留峰值检查点内存；额度不足暂停接纳，D 继续消费。
- 8 个隔离 CPU 测试已通过，包含真实 TCP 连接间的 CPU KV 传递；静态检查通过。
- Windows 环境下未完成标准 SGLang 测试入口及 CUDA 推理验证，不能把上述结果当作 GPU 验证通过。
- 旧 Rust 联合匹配文件已在工作区删除，暂未提交；保留已有数据集，不重置 Git 历史。

## 第一阶段：正确性

先按 README 启动 1P2D，GPU 3 启动相同配置的普通参考服务。
P 使用短时间片 `[1,2,4]` ms 强制触发多次迁移；短时间片只用于功能验证。

```bash
PYTHONPATH=python python test/registered/unit/disaggregation/test_mlfq.py

MLFQ_PREFILL_URL=http://127.0.0.1:30000 \
MLFQ_REFERENCE_URL=http://127.0.0.1:30004 \
PYTHONPATH=python python test/manual/test_mlfq_pd.py
```

必须验证：

- 并发请求最终 token ID 与不中断的贪心参考输出一致；流式输出没有丢失、重复或乱序。
- 日志中出现降级、Q2 回转；构造持续 Q0 到达，观察 Q1/Q2 等待超时后晋级。
- 完整 KV 确实回到 P 的 CPU 内存；从不同 D 进程恢复同一请求，并保持输出一致。
  现有 GPU 测试不保证必然跨 D，需要结合各进程日志检查，必要时补最小记录。
- 同一领取凭证只对应一次有效领取；旧回传不能覆盖新状态。
- 降低 P 内存额度触发背压：P 停止 Prefill，D 继续处理；完成后额度能够释放。
- 验证取消和 D 失联的清理行为；运行中取消按上报边界生效，失联按配置超时终止。
- 所有请求结束后，队列和预留额度清空，GPU KV 槽位可重新使用。

现有自动测试只覆盖其中一部分。没有实际检查的项目必须标为未验证。

## 第三阶段：负载与性能

正确性通过后，停止参考服务，将第四张卡加入，运行 1P3D。

- 先用固定随机种子的可控文本负载，混合短/长输入和短/长输出。
  可从输入 128/512/1024 token、输出 32/128/512 token 起步，按实际容量调整；
  这些是拟定实验档位，不是已有测量结果。用实际 tokenizer 校验长度。
- 功能与定长开销实验可使用 `ignore_eos=true`，业务负载实验恢复正常终止，分别报告。
- 请求按固定到达轨迹持续发送，逐步增加到达率，覆盖轻载、接近饱和和有限时长过载。
  记录拒绝、超时和队列增长，过载后停止注入并观察排空。
- CoQA 已下载于 `downloads/coqa/coqa-train-v1.0.json`，可作为后续多轮负载。
  打乱不同对话的交织顺序，同一对话保留轮次依赖，并明确历史答案使用数据集答案
  还是模型输出。当前关闭前缀缓存，不能用它证明缓存亲和性收益。
- 时间片先试 `[20,40,80]` ms，再根据实际单步 Decode 耗时调整；晋级阈值先试 1000 ms。
  每次只改变一个因素，各配置至少重复三次，并保留原始记录。

采集并区分以下指标：

| 指标 | 定义或用途 |
| --- | --- |
| TTFT、端到端时延 | 客户端实际发送至首 token、最终完成；报告 P50/P95/P99 |
| 吞吐与失败率 | 成功请求/秒、输出 token/秒，单独报告拒绝和超时 |
| 首次 D 等待 | Prefill KV 发布至第一次开始 Decode 的时间 |
| 恢复等待 | 回传 KV 入队至下一次开始 Decode 的时间 |
| 最大无进展间隔 | 请求未完成期间相邻进展事件的最大间隔，明确采用服务端或客户端事件 |
| 归一化慢化比 | 有负载完成时延 / 同请求相同执行路径独占运行时延；按长短请求分组 |
| 资源和迁移开销 | 各 D 显存、P 主机 RSS/预留额度、KV 字节数及迁移耗时 |

公平性不能只看平均时延：重点报告等待和慢化比尾部、长请求分组以及最差请求。
晋级阈值仅保证满足条件后晋级，不等于请求一定在该阈值内获得执行。

## 对照与交付

- 普通参考服务首先用于输出正确性。其原生执行路径与本实现不同，性能差异包含
  CPU KV 拷贝、ZMQ 和上报开销，不能全部归因于调度算法。
- 后续比较改进算法与普通 MLFQ，必须复用同一推理/传输路径、并发配置、内存预算、
  模型、负载轨迹和时间片，仅改变待研究的调度策略。当前尚无改进算法可供比较。
- 单独给出 1P1D 与 1P3D 结果，测量实际 P/D 服务耗时与积压位置，不套用固定速率比例。
- 结果保存到 `downloads/mlfq-results/<本次运行时间>/`，包含环境、命令、日志、逐请求
  数据和汇总表；该路径位于仓库已有的 downloads 忽略目录下。
- 最终报告分别列出：已通过的功能、失败与修复、测得的性能、仍未验证的内容。
  若正确性未通过，交付错误复现与修复状态，不输出算法优越性的结论。
