# 联合 Decode 匹配代码说明

对应代码：[joint.rs](joint.rs)。

## 这段代码有什么用

它负责回答一个问题：**面对一批积压请求和多个 D，本轮应该把哪些请求分配给哪些 D？**

逐个分配时，前面的短请求可能占用唯一能容纳长请求的 D。联合匹配会同时考虑整批候选组合，并允许调整计算过程中的已有选择，为其他请求腾出合适的 D。

目前它是一个独立的分配方案计算器，尚未声明为路由模块，也没有调用方，因此还没有改变实际请求的调度行为。

## 它按什么规则分配

优先级依次是：

1. 不超过各 D 提供的剩余 KV 容量。
2. 在每个请求、每个 D 本轮最多使用一次的限制下，尽量多接纳请求。
3. 接纳数量相同时，选择总收益最高的分配方案。

每个候选组合的收益为：

```text
收益 = 可复用缓存 token 数 + 请求等待毫秒数 × 等待权重
```

缓存收益用于表达亲和性；等待收益用于提高老请求的优先级。两者都服从“先尽量多接纳”的目标。它没有直接计算 TTFT，也没有保证所有请求都能在期限内执行。

## 涉及哪些结构体

Rust 这里使用结构体，没有类继承。文件中只有两个结构体，均未定义方法，也没有调用现有的 `Scheduler` 类。

### `DecodeCandidate`：一个请求与一个 D 的候选组合

| 字段 | 作用 |
| --- | --- |
| `request` | 请求在 `waiting_ms` 数组中的下标 |
| `worker` | D 在 `free_kv_tokens` 数组中的下标 |
| `required_kv_tokens` | 把这个请求分给这个 D，还需要新增多少 KV 容量 |
| `cached_tokens` | 这个 D 能为这个请求复用多少缓存 token |

同一个请求可以有多个候选 D。由于缓存位置不同，每个组合的新增容量需求和缓存收益可以不同。

`required_kv_tokens` 必须由调用方算好，包含输出预算和分页对齐；只有能够保护、确保可复用的缓存才可以从容量需求中扣除。该结构体只存结果，不负责查缓存或估算显存。

`#[derive(Debug, Clone, Copy)]` 由编译器生成调试打印和复制能力，方便查看、传递候选数据，不包含调度逻辑。

### `Edge`：匹配算法内部的一条边

| 字段 | 作用 |
| --- | --- |
| `from` | 起点编号 |
| `to` | 终点编号 |
| `available` | 算法当前能否沿这条边调整方案 |
| `cost` | 使用这条边的费用 |

边只存在于算法构建的图中，不是网络连接。`available` 也不表示 D 是否在线或显存是否充足。

## 每个函数具体做什么

### `add_edge`：添加正向边及其反向边

```rust
fn add_edge(edges: &mut Vec<Edge>, from: usize, to: usize, cost: i128) -> usize
```

输入是边数组、起点、终点和费用，输出是新建正向边的数组下标。

它往数组里连续添加两条边：

- 正向边：初始可用，费用为 `cost`，用于建立选择。
- 反向边：初始不可用，费用为 `-cost`，用于撤销选择。

正向边被使用后，反向边变为可用。后续若发现更好的整体组合，就能沿反向边撤销之前的选择，再重新分配。

两条边总是相邻，因此 `index ^ 1` 可以找到对应边：`0 ↔ 1`、`2 ↔ 3`。这省去了单独保存反向边下标的字段。

### `joint_decode_match`：计算本轮联合分配

```rust
pub fn joint_decode_match(
    waiting_ms: &[u64],
    free_kv_tokens: &[u64],
    candidates: &[DecodeCandidate],
    aging_tokens_per_ms: u32,
) -> Vec<(usize, usize)>
```

| 参数 | 调用方需要提供什么 |
| --- | --- |
| `waiting_ms` | 每个请求已经等待的毫秒数 |
| `free_kv_tokens` | 每个 D 扣除已有预留后，剩余的 KV token 容量 |
| `candidates` | 兼容、可参与本轮调度的请求与 D 组合 |
| `aging_tokens_per_ms` | 等待 1ms 折算成多少 token 的收益；为 0 时关闭等待加权 |

返回值是 `(请求下标, D 下标)` 列表。未选中的请求不出现在结果中，需由调用方保留在等待队列。

函数内部依次做以下事情。

**第一步：建立匹配图。**

```text
源点 → 请求 → D → 汇点
```

源点、汇点是算法辅助节点。每条边只能使用一次，从而保证本轮每个请求最多分给一个 D，每个 D 最多接纳一个新请求。

**第二步：加入可行的候选组合。**

检查请求、D 下标是否有效；无效下标会触发 `assert!`。若新增 KV 需求大于该 D 的剩余容量，就跳过这个组合。

其余组合按前述公式计算收益，使用 `-收益` 作为边费用。因此，寻找最低费用方案就等价于寻找最高收益方案。`i128` 用于容纳负费用和等待时间乘积。

**第三步：寻找能够增加接纳数量的最低费用路径。**

使用 Bellman–Ford 松弛过程：

- `distance` 保存从源点到各节点的当前最低费用。
- `previous` 保存到达节点时使用的边，方便回溯路径。
- `changed` 表示这一轮是否更新过费用；没有更新就提前结束搜索。

反向边可能带有负费用，因此这里没有直接使用普通 Dijkstra。

**第四步：沿路径更新分配。**

找到路径后，从汇点沿 `previous` 回溯到源点，关闭使用过的边、打开对应反向边。路径可能撤销部分旧选择，但每次完整增广都会让接纳请求数增加一个。

重复搜索，直到源点无法再到达汇点。即使最后一条路径增加总费用，仍然执行，因为最大化接纳数量的优先级更高。

**第五步：提取结果。**

`pairs` 记录每个候选组合及其正向边下标。结尾的 `filter` 闭包保留最终被使用的候选边，`map` 闭包移除内部边下标，`collect` 收集成分配列表。

## 一个具体例子

用 KV token 容量举例：

| 对象 | 容量或新增需求 |
| --- | --- |
| D-A 剩余容量 | 5000 |
| D-B 剩余容量 | 3000 |
| 短请求 | 在两个 D 上均需要 3000 |
| 长请求 | 在两个 D 上均需要 5000 |

如果先把短请求分给 A，长请求就无法接纳。联合匹配能够调整这个选择，得到：

```text
短请求 → D-B
长请求 → D-A
```

这是因为两个请求都能接纳，优于只接纳一个；并不是代码另外写了一条“短请求固定去小显存 D”的规则。

## 与完整方案的关系

| 方案目标 | 当前代码提供的能力 | 尚需接入的部分 |
| --- | --- | --- |
| D 主动选任务 | 接受候选组合，不限于队首请求 | D 上报候选、读取积压队列 |
| KV 亲和性 | 按可复用 token 数计入收益 | 真实缓存查询、缓存保护及复用路径 |
| 多 D 联合调度 | 同时匹配多请求与多 D | 资源快照、原子预留、过期校验与失败回滚 |
| P/D 异步解耦 | 尚未实现 | Prefill 结果暂存、延迟绑定 D、KV 传输 |

这里的“最优”仅针对输入快照、每轮每个 D 接纳一个请求，以及“接纳数量优先、收益其次”的目标。它还没有建模计算耗时、传输耗时和未来请求，不能代表完整系统的全局最优。

调用方还需保证候选 D 有可用请求/计算槽位，容量与缓存报告足够新，并在派发前重新校验、预留资源。算法复杂度为 `O(min(R, D) × (R + D) × (R + D + C))`，其中 R 为请求数、D 为节点数、C 为候选组合数，接入时需要限制每轮候选窗口。
